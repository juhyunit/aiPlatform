# 폐쇄망 Local AI Agent Platform 설계서

Nov 10, 2026 · @베스트

## 요약

이 설계는 상시 프로세스 4개(API 서버, 작업 워커, PostgreSQL, 모델 서버)와 얇은 자체 코드로 요구사항 전체를 담는다. 모델로 가는 길은 게이트웨이 하나이고, 작업의 완료는 모델이 아니라 테스트와 규칙 검사가 판정한다.

### 핵심 설계 결정

- **게이트웨이는 정책 필터가 먼저다.** 데이터 등급과 권한으로 허용 모델을 거르고, 그 안에서만 라우터가 고른다. 상용 모델은 레지스트리 항목, 어댑터, 정책 표 한 칸으로 추가된다.
- **모델과 실행 깊이는 독립된 두 값이다.** Quick은 LLM 1회, Thinking은 추론과 검증 1회, Agent는 상태 기계가 이끄는 반복 루프다.
- **Agent Runtime과 Workflow Engine을 나눈다.** 도구를 고르는 것은 모델이고, 다음 단계와 종료를 정하는 것은 코드다.
- **검증은 실행 기반, 규칙 기반, LLM 검토 순이다.** LLM 검토는 문제 제기만 할 수 있다.
- **저장소는 PostgreSQL 하나다.** 업무 데이터, 벡터, 체크포인트, 작업 큐, 감사 로그를 함께 둔다.
- **폐쇄망 규칙은 0단계부터 적용한다.** 네트워크를 끈 테스트를 처음부터 돌린다.
- **하네스 기법마다 켜고 끄는 설정을 둔다.** 2단계에서 효과를 측정하고, 효과가 없는 것은 3단계에서 삭제한다.

### 요구사항과 다르게 판단한 점

| 요구사항 | 이 설계의 판단 | 근거 |
| --- | --- | --- |
| Qwen 등을 연결 모델 예시로 제시. MinerU, PaddleOCR 검토 | 내부 이식 후보는 출처 심사를 먼저 거친다. Qwen, MinerU, PaddleOCR, BGE 임베딩은 중국 기관·기업 개발 | 첨부 가이드 7장, 부록 A |
| 역할별 에이전트 9종 | 프로필 3개(Planner, Worker, Reviewer)와 결정적 도구 | 역할이 늘면 컨텍스트 손실과 호출 수가 늘고, 테스트 실행에는 추론이 필요 없다 |
| 개발 14단계 흐름 | 5단계 상태 기계에 14단계를 점검 항목으로 배치 | 같은 이유 |
| 상용 AI 코딩 에이전트처럼 자율 수행 | 방향으로만 삼는다. 성공 기준은 자체 평가셋 통과율 | 보유 GPU에서 도는 모델과 최상위 모델의 격차는 하네스로 메울 수 없다 |
| Colab Pro로 추론 테스트, RunPod에서 서버 수행 | Colab은 모델 벤치마크 전용, RunPod은 모델 서버 전용. 폐쇄망 리허설은 OS를 통제할 수 있는 서버가 따로 필요 | Colab은 대화형 연산과 무관한 웹 서비스 제공을 금지하고, RunPod Pod는 안에서 Docker를 띄울 수 없다(15장) |
| 기성 오픈소스 조합 | 게이트웨이, Agent Runtime, UI는 자체 구현 | LiteLLM은 2026년 공급망 사고 2회, Open WebUI는 브랜딩 조항 |

### 착수 전에 정해야 하는 것

- [ ] 사내에 놓일 GPU의 종류와 수량. 2단계에서 빌릴 GPU와 모델 후보가 여기서 정해진다
- [ ] 목표 동시 사용자 수. 부하 테스트의 통과 기준이 된다
- [ ] 모델·보조 모델의 출처 허용 기준. 정보보호 부서 확인
- [ ] 데이터 등급 체계 초안. 게이트웨이 정책 표와 문서 태그에 쓴다
- [ ] 개발 PC의 GPU 사양. 0\~1단계에서 쓸 모델 크기가 정해진다
- [ ] 우선 업무 3\~5개와 평가 문항을 만들 현업 담당자

## 1. 프로젝트 개요 및 구축 목표

사내 폐쇄망에서 오픈 가중치 LLM으로 문서 분석, 데이터 분석, 프로그램 개발, 사내 지식 검색을 끝까지 수행하는 범용 에이전트 플랫폼을 만든다. 모델을 설치해 채팅하는 것이 목적이 아니다. 모델의 약점을 실행 구조(하네스)로 보완해 '답변'이 아니라 '검증된 작업 결과'를 내놓는 것이 목적이다.

| 목표 | 달성 기준 (측정 가능해야 한다) |
| --- | --- |
| 폐쇄망 독립 | 외부 통신 0건 상태에서 전 기능 동작. 모델·패키지 오프라인 설치와 업데이트 |
| 모델 독립 | 새 모델 추가가 레지스트리 등록과 회귀 평가로 끝난다. 업무 코드 수정 없음 |
| 속도와 깊이의 분리 | 단순 질의는 LLM 1회 호출로 응답. 복합 작업만 계획·검증 루프에 진입 |
| 작업 완결 | 자체 평가셋에서 객관적 검증(테스트·스키마·규칙)을 통과한 비율로 성공을 판정 |
| 통제 가능 | 사용자 권한·문서 등급·도구 권한이 모든 실행 경로에 적용되고 전수 기록 |
| 상용 모델 확장 대비 | '데이터 등급 → 실행 환경 → 모델' 순서의 판단 구조를 처음부터 내장 |

설계 전제는 세 가지다. GPU가 제한적이고, 은행 내부망에 이식해야 하며, 소규모 인력이 PC와 Colab Pro로 개발을 시작한다. 그래서 이 설계서는 구성요소 수를 줄이는 것을 기능을 늘리는 것보다 우선한다.

범위에서 제외한 것은 다음과 같다. 근거는 각 절에 적었다.

- 모델 파인튜닝. 지식은 검색으로, 행동은 도구로 넣어야 모델을 바꿔도 자산이 남는다.
- 대고객 서비스와 대출 심사 등 고영향 업무. 내부 임직원 업무 보조로 한정한다.
- 사람 승인 없이 외부 시스템 상태를 바꾸는 행위(운영 DB 쓰기, 메일 발송 등).

## 2. 상용 AI 에이전트 대비 핵심 가치와 한계 인식

이 플랫폼의 가치는 성능이 아니라 통제권이다. 상용 에이전트보다 똑똑해질 수는 없다. 대신 상용 에이전트가 들어올 수 없는 데이터 영역에서, 은행이 정한 규칙대로 같은 방식의 일을 시킬 수 있다.

| 항목 | 상용 AI 에이전트 | 이 플랫폼 |
| --- | --- | --- |
| 데이터 위치 | 외부 전송 전제. 개인신용정보·고유식별정보는 현행 SaaS 망분리 예외 대상이 아님(첨부 가이드 3장) | 내부망에서 처리 |
| 모델 선택 | 공급자가 정함 | 레지스트리 등록과 자체 평가로 교체 |
| 통제 기준 | 공급자 정책 | 은행의 데이터 등급, 권한, 감사 기준 |
| 검증 과정 | 내부 동작 비공개 | 단계별 검증 결과와 증거를 기록 |
| 추론 성능 | 최상위 | 격차가 있음. 아래 참조 |

성능 격차는 설계로 없앨 수 없다. 첨부 가이드가 인용한 Epoch AI 측정에 따르면 최상위 오픈모델은 폐쇄형 최상위보다 평균 4개월, 단일 소비자용 GPU에서 도는 모델은 6\~12개월 뒤진다. 따라서 '상용 에이전트 수준의 자율 수행'은 달성 기준이 아니라 방향이다. 성공 여부는 자체 평가셋의 통과율로만 판정한다.

### 하네스가 보완하는 것과 보완하지 못하는 것

| 모델의 약점 | 보완 수단 | 보완 정도 |
| --- | --- | --- |
| 사내 지식이 없음 | RAG | 큼 |
| 계산·집계 오류 | 코드 실행 결과를 답에 사용 | 큼 |
| 출력 형식과 도구 호출 형식이 깨짐 | 구조화 출력(문법 제약 디코딩) | 큼 |
| 긴 작업에서 앞 내용을 잊음 | 컨텍스트 압축, 작업 상태 파일 | 중간 |
| 자기 결과의 오류를 못 찾음 | 테스트·규칙 검증 후 재시도 | 중간. 검증 수단이 있는 작업에 한함 |
| 이미지·도표 인식 한계 | OCR 병행 | 중간 |
| 추론 깊이와 장기 계획 능력 부족 | 작업 분해로 일부 완화 | 작음. 더 나은 모델로 교체하는 것이 답 |

마지막 행이 이 프로젝트의 가장 큰 위험이다. 하네스 기법을 더 쌓는 것으로 해결하려 하지 말고, 모델 교체가 쉬운 구조를 유지하는 데 노력을 쓴다.

## 3. 전체 시스템 아키텍처

시스템은 UI, API 서버, 실행 계층, 공통 모듈, 저장소·모델 서버의 다섯 층이다. 세 실행 모드는 같은 공통 모듈을 쓰고, 모델로 가는 길은 Model Gateway 하나뿐이다.

색이 칠해진 Model Gateway가 유일한 모델 진입점이다. 점선 상자인 상용 모델은 지금 없지만, 추가될 때 게이트웨이 아래에만 붙는다.

요청 하나는 다음 순서로 흐른다.

1. UI가 메시지, 첨부, 모드, 모델 선택을 보낸다.
2. API 서버가 사용자와 권한을 확인하고 세션을 불러온다.
3. 모드 라우터가 실행 경로를 정한다.
4. 실행 경로가 파일 처리, 검색, 컨텍스트 조립을 거쳐 게이트웨이를 호출한다.
5. 게이트웨이가 데이터 등급으로 허용 모델을 거르고, 그 안에서 모델을 고른다.
6. 결과는 검증기를 거쳐 스트리밍되고, 모든 단계가 추적 표에 남는다.

GPU가 필요한 것은 모델 서버뿐이다. 나머지는 CPU 호스트에서 돈다. 이 분리 덕분에 개발 PC, RunPod, 사내 서버에서 같은 구성을 쓸 수 있다. 바뀌는 것은 모델 서버의 주소뿐이다.

## 4. 모듈별 상세 기능 및 역할

모듈은 12개이고, 상시 실행 프로세스는 4개(API 서버, 작업 워커, PostgreSQL, 모델 서버)다. 모듈은 파이썬 패키지 단위로 나누고 인터페이스로만 호출한다. 프로세스 경계는 모델 서버, 샌드박스, DB에만 둔다.

| 모듈 | 책임 | 초기 구현 | 뒤로 미룬 것 |
| --- | --- | --- | --- |
| Web UI | 채팅, 파일 첨부·미리보기, 모드·모델 선택, 작업 진행 표시, 결과물 다운로드, 이력 | 단일 페이지 앱, SSE 스트리밍 | 관리자 콘솔 |
| API 서버 | 인증, 권한, 세션, 요청 접수, 이벤트 스트림 | FastAPI, 무상태 | 다중 인스턴스 |
| 모드 라우터 | Auto 판정, 실패 시 상위 모드로 승격 | 규칙 + 소형 모델 분류 | 학습형 라우터 |
| Model Gateway | 모델 레지스트리, 정책 필터, 모델 라우팅, 엔진 어댑터, 장애 전환, 사용량 계측 | OpenAI 호환 API 한 종류로 통일 | 상용 모델 어댑터 |
| Prompt Manager | 역할·업무별 프롬프트, 모델별 패치, 버전 | Git으로 관리하는 템플릿 파일. 버전은 커밋 해시 | 프롬프트 편집 UI |
| Context Manager | 토큰 예산 배분, 이력 요약·압축, 상태 재주입 | 슬롯별 예산, 임계치 압축 | 학습 기반 압축 |
| Agent Runtime | 한 역할의 한 단계를 도구를 써서 수행하는 루프 | 자체 구현 | 병렬 하위 에이전트 |
| Workflow Engine | 계획, 단계 상태, 관문, 예산, 체크포인트, 사람 승인 | 상태 그래프 + DB 체크포인트, 템플릿 3종 | 템플릿 편집기 |
| Tool Manager·샌드박스 | 도구 등록, 권한 등급, 승인, 격리 실행 | Python 실행, 파일 읽기·생성, 데이터 분석, 문서 변환, 검색 | SQL, REST, MCP |
| Knowledge·Memory | 색인, 하이브리드 검색, 리랭킹, 출처, 접근권한 필터, 기억 4종 | PostgreSQL + pgvector 한 곳 | 장기 기억 자동 추출 |
| File Pipeline | 형식 판별, 파싱, OCR, 공통 문서 표현, 결과 파일 생성 | PDF, Office, HWPX, 이미지, CSV, 코드 | HWP 바이너리 |
| Validator | 형식·스키마·규칙 검사, 테스트 실행, 인용 확인, LLM 검토 | 실행·규칙 검증 우선 | UI 시각 검수 |

평가·관측은 독립 모듈이 아니라 모든 모듈이 지키는 규약이다. 모든 요청에 추적 ID를 붙이고, LLM 호출·도구 호출·검증 결과를 같은 표에 남긴다. 평가 러너는 이 기록과 평가셋을 읽어 점수를 낸다.

프롬프트를 바꾸면 코드 변경과 똑같이 회귀 평가를 통과해야 반영된다. 모델별 최적화는 기본 프롬프트를 복사하지 않고 차이만 담은 패치 파일로 둔다. 모델을 교체할 때 손댄 범위가 패치 파일로 한정된다.

## 5. Agent Runtime과 Workflow Engine의 구조적 차이

Agent Runtime은 '이 단계를 어떻게 수행할까'를 모델이 정하는 루프이고, Workflow Engine은 '다음에 무엇을 하고 언제 끝낼까'를 코드가 정하는 상태 기계다. 둘을 나누는 이유는 흐름 제어와 완료 판정을 모델에게 맡기지 않기 위해서다. 소형 모델은 일을 덜 끝내고 완료를 선언하거나 같은 시도를 반복하는 경우가 많다.

| 구분 | Agent Runtime | Workflow Engine |
| --- | --- | --- |
| 결정 주체 | LLM. 어떤 도구를 어떤 인자로 부를지 | 코드. 상태 전이 규칙과 검증 결과 |
| 실행 단위 | 한 역할의 한 단계 | 작업 전체 |
| 상태 | 메시지 목록. 단계가 끝나면 요약과 산출물 경로만 반환하고 버림 | 계획, 단계 상태, 산출물, 예산. DB에 체크포인트 |
| 실패 처리 | 도구 오류를 읽고 재시도. 횟수 상한 있음 | 실패한 단계로 회귀. 예산 초과 시 중단 |
| 사람 개입 | 위험 도구 실행 승인 | 명세 승인, 일시 정지, 재개, 취소 |
| 쓰이는 모드 | Thinking(도구가 필요할 때), Agent | Agent |
| 구현 | 자체 구현. 도구 호출 루프와 종료 조건 | LangGraph 상태 그래프 + PostgreSQL 체크포인터 |

Agent Runtime을 직접 구현하는 이유는 로컬 모델마다 다른 도구 호출 형식과 오류 양상을 직접 다뤄야 하기 때문이다. Workflow Engine에 LangGraph를 쓰는 이유는 체크포인트, 중단, 재개를 직접 만들면 비용이 크기 때문이다. LangGraph는 Workflow Engine 인터페이스 뒤에만 두어, 의존성 심사에서 탈락하면 자체 상태 기계로 바꿀 수 있게 한다.

### 역할은 프로세스가 아니라 프로필이다

역할 하나는 `{시스템 프롬프트, 허용 도구, 컨텍스트 정책, 모델·추론 설정}` 묶음이다. 같은 Agent Runtime에 프로필만 바꿔 끼운다. 요구사항의 9개 역할은 프로필 3개와 결정적 도구로 줄인다.

| 요구사항의 역할 | 이 설계에서 | 이유 |
| --- | --- | --- |
| PM, Architect | Planner 프로필 | 명세와 계획은 같은 컨텍스트에서 써야 어긋나지 않는다 |
| Developer, Data Analyst | Worker 프로필. 업무별로 도구와 프롬프트만 다름 | 루프 구조가 같다 |
| Test Agent | 에이전트가 아니라 테스트 실행 도구 | 테스트 실행과 판정에는 추론이 필요 없다 |
| Security Reviewer | 정적 분석 도구 + Reviewer 프로필의 보안 점검표 | 도구가 찾은 것이 우선이고 LLM은 해석을 돕는다 |
| UI/UX Reviewer, QA, Critical Reviewer | Reviewer 프로필. 점검표만 다름 | 아래 참조 |

Reviewer가 Worker와 같은 모델이면 같은 맹점을 공유한다. 그래도 쓸모가 있는 이유는 세 가지다. 작업 과정을 보지 않은 새 컨텍스트에서 결과물만 본다. 점검표를 항목별로 확인한다. 문제를 제기할 때 재현 가능한 검사(실패하는 테스트, 어긋난 수치)를 함께 내야 한다. 역할을 더 늘리면 단계마다 컨텍스트가 유실되고 호출 수만 늘어난다. 프로필 추가는 평가에서 효과가 확인될 때만 한다.

## 6. 모델 게이트웨이, 자동 라우팅, 상용 모델 확장 기반

모델 선택은 두 단계로 한다. 먼저 정책이 쓸 수 있는 모델의 집합을 정하고, 그 안에서만 라우터가 고른다. 이 순서는 첨부 가이드 6장의 판단 구조를 그대로 구현한 것이고, 상용 모델을 나중에 붙일 수 있는 근거다.

### 게이트웨이 구조

내부 표준 API는 OpenAI 호환 Chat Completions 하나로 정한다. vLLM, SGLang, llama.cpp, Ollama가 모두 이 형식을 제공하므로 어댑터가 얇아진다. 게이트웨이는 자체 구현한다.

1. **정책 필터(거부권).** 요청에 포함된 데이터의 최고 등급과 사용자 권한으로 허용 모델 집합을 구한다. 집합이 비면 요청을 거부한다. 등급은 문서·파일·세션에 붙은 태그에서 읽는다. 모델이 민감도를 추정하게 하지 않는다.
2. **라우터(최적화).** 허용 집합 안에서 작업 유형, 필요한 능력(비전, 도구 호출, 컨텍스트 길이), 자체 평가 점수를 보고 가장 가벼운 합격 모델을 고른다. 사용자가 모델을 지정했으면 그 모델이 허용 집합에 있는지만 확인한다.
3. **어댑터.** 모델별 차이를 흡수한다. 도구 호출은 모델의 고유 형식을 믿을 수 있으면 그대로 쓰고, 아니면 JSON 스키마 제약 출력으로 통일한다. 추론 강도는 `off / low / high`로 표준화해 모델별 파라미터로 바꾼다.
4. **장애 전환과 계측.** 헬스 체크에 실패한 모델은 차단하고, 허용 집합 안의 다음 모델로 보낸다. 전환 사실, 토큰 수, 지연 시간을 응답 메타데이터와 감사 로그에 남긴다.

모델과 실행 깊이는 독립된 두 값이다. 요청은 `model`(auto 또는 모델 ID)과 `mode`(auto, quick, thinking, agent)를 따로 받는다. 소형 모델의 Thinking, 대형 모델의 Quick이 모두 가능하다.

LiteLLM을 쓰지 않는 이유는 공급망 사고 이력과 범위 과잉이다. 2026년 10월 21일 1.107.0 악성 릴리스가 PyPI와 공식 Docker 이미지로 약 2시간 배포됐고, 그보다 앞서 1.82.7·1.82.8도 침해됐다([Datadog Security Labs](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-docker.md)). 게이트웨이는 모든 요청과 자격증명이 지나는 자리이고, 이 플랫폼에 필요한 어댑터는 한두 종류뿐이다.

### 모델 레지스트리

레지스트리 한 항목이 모델의 연결 정보, 출처, 라이선스, 자원 요구량, 평가 점수를 모두 갖는다. `env`와 `clearance`는 지금은 값이 하나뿐이지만 처음부터 둔다.

```yaml
id: gemma4-31b-awq
engine: vllm
endpoint: http://deep-pool:8000/v1
env: internal            # internal | external
clearance: pii           # 이 환경이 받을 수 있는 최고 데이터 등급
provenance: {developer: Google, license: Apache-2.0, sha256: "..."}
capabilities: {vision: true, tools: native, reasoning: [off, high], context: 32768}
resources: {vram_gb: 24, quant: awq-4bit}
eval: {ko_qa: 0.00, coding: 0.00, tool_call: 0.00}   # 자체 평가셋 점수, 측정 후 기입
status: active
```

### 데이터 등급과 상용 모델 확장

상용 모델을 추가하는 일은 세 가지로 끝나야 한다. 레지스트리에 `env: external` 항목을 넣고, 공급자 API용 어댑터를 추가하고, 아래 표의 해당 칸을 켠다. 표는 첨부 가이드의 예시이며 등급 체계는 은행이 확정한다.

| 데이터 등급(예시) | 내부망 모델 | 승인된 외부 상용 모델 |
| --- | --- | --- |
| 공개 | 허용 | 허용 |
| 내부 일반 | 허용 | 대체 통제 충족 시 |
| 내부 중요(전략, 소스코드) | 허용 | 개별 승인 |
| 가명정보 | 허용 | 혁신금융 지정 시에만 |
| 개인신용정보·고유식별정보 | 허용 | 불가(현행) |

외부 경로에는 추가 통제가 붙는다. 전송 전 등급 재확인과 민감정보 패턴 검사, 공급자별 차단 스위치, 별도 감사 로그, 공급자 2곳 이상으로 전환 가능한 어댑터다. 마스킹한 데이터를 외부로 보내는 방식은 등급 필터를 대신하지 못한다. 가명정보도 개인정보다(첨부 가이드 부록 A).

### 자동 라우팅과 평가

라우터는 모델 크기가 아니라 업무 유형별 자체 평가 점수를 본다. 평가 유형은 한국어 질의응답, 수리 추론, 코딩, 문서 이해, 이미지 분석, 도구 호출 6가지로 시작한다. 학습형 라우터는 운영 로그가 쌓인 뒤에 검토한다.

## 7. Quick / Thinking / Agent 실행 방식

세 모드는 LLM 호출 횟수와 검증 강도가 다르고, Auto는 그중 하나를 고르는 판정기다. 기본값은 Auto이고, 사용자가 지정하면 그대로 따른다.

| 모드 | 실행 경로 | 추론 | 도구 | 검증 |
| --- | --- | --- | --- | --- |
| Quick | 컨텍스트 조립 후 LLM 1회 호출. 첨부나 사내 지식 질문이면 검색 1회 추가 | 끔 | 없음 | 형식 검사만 |
| Thinking | 추론을 켠 단일 에이전트. 검색을 여러 번 할 수 있음 | 켬 | 읽기 전용 도구, 계산용 코드 실행 | 인용 실재 확인, 수치 재계산, 형식. 실패 시 1회 수정 |
| Agent | Workflow Engine이 명세, 계획, 실행, 검증, 요구사항 대조를 진행 | 단계별 설정 | 쓰기 도구 포함, 샌드박스 | 실행 기반 검증. 예산 안에서 반복 |

### Auto 판정 순서

1. 규칙으로 먼저 가른다. 파일·프로그램·보고서 같은 산출물 생성 요청과 다단계 지시는 Agent 후보다. 계산, 비교, 원인 분석은 Thinking 후보다. 나머지는 Quick이다.
2. 규칙으로 가르지 못한 요청만 소형 모델이 분류한다. 출력은 JSON 스키마로 강제하고 토큰 상한을 작게 둔다.
3. Auto가 Agent를 고르면 실행 전에 계획과 예상 단계를 보여주고 확인을 받는다. Agent는 비용이 커서 잘못 고르면 손해가 크다.
4. 승격만 있고 강등은 없다. Quick 응답이 형식 검사에 걸리거나 사용자가 '더 깊게'를 누르면 Thinking으로 다시 실행한다.

추론을 끄고 켜는 방법은 모델마다 다르다. 게이트웨이 어댑터가 처리하고, 추론 제어가 없는 모델은 '풀이를 먼저 쓰고 답을 낸다'는 2단 프롬프트로 대신한다.

### 사용자에게 보여주는 진행 정보

화면에는 모델의 내부 추론 전문이 아니라 실행 이벤트를 표시한다. 서버는 아래 이벤트를 SSE로 보내고, 같은 내용을 추적 표에 저장한다.

| 이벤트 | 내용 |
| --- | --- |
| `plan` | 작업 계획과 완료 조건 |
| `step_started`, `step_done` | 현재 단계, 담당 프로필, 단계 요약 |
| `tool_call`, `tool_result` | 실행한 도구와 인자, 결과 요약 |
| `check_result` | 테스트·규칙 검사의 통과와 실패 |
| `issue`, `fix` | 발견된 문제, 수정과 재검증 결과 |
| `approval_required` | 사용자 승인 요청 |
| `run_done` | 완료 여부, 충족하지 못한 항목, 산출물 목록 |

응답 속도 목표치는 지금 정하지 않는다. 2단계에서 목표 모델로 기준선을 잰 뒤 모드별 첫 토큰 시간과 완료 시간 목표를 확정한다.

## 8. 파일 및 멀티모달 처리 구조

모든 파일은 형식별 파서를 거쳐 하나의 공통 문서 표현으로 바뀐다. 청킹, 검색, 인용, 문서 비교는 이 표현 위에서만 동작한다. 모델이 파일을 직접 이해한다고 가정하지 않는다.

공통 표현은 블록의 목록이다. 블록마다 종류(제목, 문단, 표, 그림), 텍스트, 페이지, 위치, 표의 셀 구조를 갖는다.

| 형식 | 1차 처리 | 보완 |
| --- | --- | --- |
| PDF(텍스트) | Docling으로 레이아웃과 표 구조 추출 | 단순 텍스트 추출은 pypdfium2 |
| PDF(스캔), 스캔 문서 | OCR 후 레이아웃 분석 | 품질이 모자라면 비전 모델로 페이지 단위 재처리 |
| Word, PowerPoint | Docling | 슬라이드의 그림은 비전 모델로 설명 생성 |
| Excel, CSV | 파일을 샌드박스에 그대로 두고 pandas·openpyxl로 처리 | 프롬프트에는 열 이름, 자료형, 표본 행, 요약 통계만 넣음 |
| HWPX | zip + XML 구조라 직접 파싱 | Docling에 HWPX 백엔드가 제안됨([PR #3856](https://github.com/docling-project/docling/pull/3856)). 병합 여부 확인 후 사용 |
| HWP(5.x 바이너리) | HWPX로 변환 후 같은 경로 | 변환기 후보: rhwp(MIT), [hwp2hwpx](https://github.com/neolord0/hwp2hwpx)(Apache 2.0, Java) |
| 이미지, 차트 | 비전 모델 + OCR 텍스트를 함께 제공 | 차트의 수치는 원본 데이터가 있으면 그쪽을 우선 |
| 코드 | 텍스트 그대로, 언어 판별 | 큰 저장소는 파일 목록과 검색 도구로 접근 |

HWP가 가장 위험한 형식이다. Docling HWPX 제안은 차트, 글상자, 머리말·꼬리말, 배포용(DRM) 문서를 처리하지 않고, 바이너리 HWP는 후속 작업으로 남겨 두었다. 3.x 이하 구버전과 변환 실패 문서는 'PDF로 저장해 다시 올려 달라'고 안내한다. HWP 바이너리는 초기 필수 범위에서 뺀다.

### 처리 규칙

- **크기에 따라 세 가지로 처리한다.** 작은 파일은 전문을 컨텍스트에 넣는다. 중간 크기는 세션 한정 색인을 만들어 검색한다. 큰 파일은 구간별 요약을 먼저 만들고 검색과 함께 쓴다. 경계는 모델의 컨텍스트 예산 대비 비율로 정한다.
- **표 데이터는 프롬프트에 붓지 않는다.** 집계와 계산은 샌드박스의 코드가 하고, 모델은 코드를 쓰고 결과를 해석한다.
- **문서 비교는 코드가 차이를 찾고 모델이 의미를 설명한다.** 제목·조항 단위로 정렬한 뒤 텍스트 차이를 계산한다.
- **결과 파일은 코드 실행으로 만든다.** Word, Excel, PowerPoint는 python-docx, openpyxl, python-pptx로 생성한다. HWPX는 서식 템플릿의 XML을 채우는 방식으로 한다.
- **파싱은 격리된 프로세스에서 한다.** 파일은 신뢰할 수 없는 입력이다. 크기, 페이지 수, 압축비에 상한을 둔다.

| --- | --- | --- | --- | --- |

OCR 엔진은 한 가지로 정하지 않고 인터페이스 뒤에 둔다. 실제 은행 문서 표본으로 한국어 인식률을 측정해 고르고, 선택한 엔진과 모델 파일의 출처를 레지스트리에 기록한다.

## 9. RAG, Memory, Context Engineering 설계

세 가지 모두 PostgreSQL 한 곳에 저장한다. 벡터 검색, 키워드 검색, 접근권한 필터를 한 SQL 안에서 처리할 수 있고, 운영할 저장소가 하나로 줄기 때문이다.

### RAG

1. **청킹.** 공통 문서 표현의 제목 구조를 따라 자른다. 표는 쪼개지 않는다. 청크마다 문서 ID, 페이지, 제목 경로, 보안등급, 접근 그룹을 붙인다.
2. **색인.** 밀집 벡터는 pgvector의 HNSW 색인에 넣는다. 키워드는 형태소 분석기(Kiwi)로 토큰화해 PostgreSQL 전문 검색 색인에 넣는다. 한국어는 공백 단위 토큰화로는 검색이 잘 되지 않는다.
3. **검색.** 권한 필터를 먼저 적용한 뒤 밀집 검색과 키워드 검색을 각각 수행하고 순위 융합(RRF)으로 합친다.
4. **리랭킹.** 상위 30개 안팎을 교차 인코더 리랭커로 다시 정렬해 8개 안팎만 컨텍스트에 넣는다. 개수는 평가로 조정한다.
5. **출처.** 답변은 청크 ID로 인용한다. 검증기가 인용된 ID가 검색 결과에 실제로 있는지 확인하고, 화면에는 문서명과 페이지로 표시한다.

권한 필터는 검색 뒤가 아니라 검색 조건으로 건다. `문서 등급 ≤ 사용자 등급`, `문서 등급 ≤ 모델 환경 허용 등급`, `접근 그룹 일치` 세 조건을 모두 만족하는 청크만 순위 계산에 들어간다. 행 수준 보안(RLS)을 두 번째 방어선으로 켠다.

| 구성요소 | 선정 | 라이선스 | 대안 |
| --- | --- | --- | --- |
| 벡터 저장 | PostgreSQL + pgvector | PostgreSQL License | Qdrant, Milvus. 문서 수가 크게 늘어 검색 지연이 문제가 될 때 |
| 키워드 검색 | Kiwi 토큰화 + PostgreSQL 전문 검색 | Kiwi는 [LGPL v3](https://www.pypi.org/project/kiwipiepy/0.5.0/) | BGE-M3의 희소 벡터를 pgvector `sparsevec`에 저장([0이 아닌 차원 1,000개까지 색인](https://postgrespro.com/list/id/171446388084.707.10085496804414536429@wrigleys.postgresql.org)) |
| 임베딩 | [KURE-v1](https://huggingface.co/nlpai-lab/KURE-v1) 또는 BGE-M3 | 둘 다 MIT | KURE-v1은 고려대가 BGE-M3를 한국어로 추가 학습한 모델. BGE-M3는 중국 기관(BAAI) 개발 |
| 리랭커 | 다국어 교차 인코더 | 모델별 확인 | 리랭커 없이 시작하고 평가에서 효과가 있을 때 추가 |

임베딩 모델도 출처 심사 대상이다. 한국어 성능이 좋은 공개 임베딩은 상당수가 BGE 계열이거나 그 파생이다. 생성 모델보다 위험은 낮지만 판단은 은행의 출처 기준에 따른다. 임베딩을 바꾸면 전체 재색인이 필요하므로, 색인마다 임베딩 모델 ID를 기록한다.

### Memory

| 종류 | 내용 | 저장 위치 | 초기 범위 |
| --- | --- | --- | --- |
| 단기 대화 기억 | 세션의 메시지 | 메시지 표 | 포함 |
| 작업 기억(Working Memory) | 계획, 단계 요약, 산출물 경로 | 워크플로 체크포인트 + 작업 폴더 파일 | 포함 |
| 작업 이력 | 과거 실행의 요청, 결과, 검증 기록 | 실행 기록 표 | 조회만 포함. 유사 작업 자동 참조는 후순위 |
| 장기 기억 | 사용자가 저장을 승인한 선호와 사실 | 기억 표 + 벡터 색인 | 수동 저장만 포함. 자동 추출은 후순위 |

모든 기억은 소유자(사용자 또는 에이전트 프로필)와 보안등급을 갖고, 검색과 같은 권한 필터를 거친다. 장기 기억 자동 추출을 미루는 이유는 잘못 추출된 기억이 이후 답변을 조용히 오염시키고 원인을 찾기 어렵기 때문이다.

### Context Engineering

호출마다 컨텍스트를 슬롯별 예산으로 조립한다. 비율은 출발값이고 평가로 조정한다.

| 슬롯 | 예산(출발값) | 규칙 |
| --- | --- | --- |
| 시스템 프롬프트, 역할, 도구 정의 | 15% 이하 | 맨 앞에 두고 내용과 순서를 고정. 접두부 캐시가 적중한다 |
| 검색 결과, 첨부 발췌 | 35% 이하 | 리랭킹 순서대로 예산까지만 |
| 대화·실행 이력 | 25% 이하 | 초과하면 오래된 것부터 요약으로 교체 |
| 작업 상태(계획, 현재 단계, 완료 조건) | 10% 이하 | 매 호출 끝부분에 다시 넣음 |
| 출력 예약 | 15% 이상 | 모드별 최대 출력 토큰으로 제한 |

- 도구 결과가 크면 파일로 저장하고, 컨텍스트에는 앞부분 미리보기와 경로만 넣는다.
- 단계가 끝나면 그 단계의 컨텍스트를 버리고, 요약과 산출물 참조만 다음 단계에 넘긴다. 장기 작업에서 컨텍스트가 유지되는 것은 이 구조 덕분이다.
- 압축은 예산의 70%를 넘을 때 수행한다. 원문은 DB에 남겨 필요하면 검색해 복원한다.
- 오류 메시지와 실패한 테스트 출력은 요약하지 않는다. 수정의 근거가 되기 때문이다.

개발 PC에서는 컨텍스트를 8K\~16K 토큰으로 잡게 된다. 예산 조립기는 0단계에서 먼저 만들어야 이후 기능이 작은 컨텍스트에서도 동작한다.

## 10. 자율 계획·실행·테스트·검수·반복 개선 구조

Agent 모드는 다섯 단계와 두 개의 관문으로 된 상태 기계다. 관문을 여는 것은 모델의 '다 했다'는 말이 아니라 테스트와 규칙 검사의 결과다.

&#91;embedded content: 자율 작업 루프 · 5개 단계, 관문 2개, 회귀 경로 2개\]

검증에 실패하면 오류 출력을 들고 실행으로 돌아가고, 요구사항이 빠졌으면 계획으로 돌아간다. 단계가 끝날 때마다 상태를 DB에 저장하므로 중단된 작업은 마지막 단계부터 재개된다.

### 단계별 내용

| 단계 | 수행 | 하는 일 | 다음으로 넘어가는 조건 |
| --- | --- | --- | --- |
| 명세 | Planner | 요구사항을 확인 가능한 완료 조건 목록으로 정리 | 사용자 승인 |
| 계획 | Planner | 단계 분해, 단계별 산출물과 검증 방법 지정. 개발 업무는 구조 설계 포함 | 모든 완료 조건이 최소 한 단계에 연결됨(코드로 확인) |
| 실행 | Worker | 단계를 하나씩 수행. 단계마다 새 컨텍스트 | 단계별 검사 통과 |
| 검증 | 검증기, Reviewer | 전체 테스트, 정적 분석, 규칙 검사. Reviewer는 새 컨텍스트에서 점검표 확인 | 실행·규칙 검사 전부 통과 |
| 요구사항 대조 | 코드 + Reviewer | 완료 조건마다 증거(테스트 ID, 검사 결과, 산출물 위치)를 연결 | 증거 없는 조건 0개 |

요구사항의 개발 14단계는 이 다섯 단계에 들어간다. 1\~2는 명세, 3\~4는 계획, 5\~7은 실행, 8\~10은 검증, 11은 요구사항 대조, 12\~13은 회귀 경로, 14는 완료다. 14단계를 각각 다른 에이전트의 단계로 만들지 않은 이유는 단계가 늘수록 넘겨주는 과정의 정보 손실과 호출 수가 함께 늘기 때문이다.

### 검증 수단의 우선순위

| 순위 | 종류 | 예 | 권한 |
| --- | --- | --- | --- |
| 1 | 실행 기반 | 단위·통합 테스트, 빌드, 쿼리 재실행, 수치 재계산 | 통과와 실패를 결정 |
| 2 | 규칙 기반 | 스키마, 린트, 정적 분석, 인용 실재 확인, 필수 항목 존재 | 통과와 실패를 결정 |
| 3 | LLM 검토 | Reviewer의 점검표 확인 | 문제 제기만 가능. 재현 가능한 검사로 바뀌어야 실패로 처리 |

가독성처럼 실행이나 규칙으로 판정할 수 없는 항목은 LLM 검토 의견을 '참고'로 표시해 사용자에게 넘긴다. 완료 판정에는 쓰지 않는다.

### 업무 유형별 객관적 검증

| 업무 | 검증 수단 |
| --- | --- |
| 프로그램 개발 | 단위·통합 테스트, 빌드, 린트, 타입 검사, 보안 정적 분석 |
| 데이터 분석 | 코드 재실행 결과 일치, 행 수·합계 대사, 결과 스키마 |
| 문서 분석 | 인용 구절이 원문과 일치, 페이지 번호 유효, 질문 항목 전부에 응답 |
| 보고서 작성 | 필수 목차 존재, 모든 수치의 출처 추적, 분량·형식 |

### 예산과 사람의 개입

- 예산은 세 가지다. 단계당 수정 횟수, 전체 실행 시간, 전체 토큰. 기본값은 2단계에서 성공한 작업의 분포를 보고 정한다.
- 예산을 넘으면 완료된 부분, 남은 조건, 마지막 실패 원인을 정리해 사용자에게 넘긴다. 부분 결과를 완료로 표시하지 않는다.
- 사용자는 언제든 일시 정지, 재개, 취소할 수 있고, 정지한 동안 완료 조건과 계획을 고칠 수 있다.
- 외부에 영향을 주는 도구는 실행 전에 승인을 요청하고, 승인이 올 때까지 그 자리에서 멈춘다.

## 11. 로컬 LLM 추론 성능 최적화 전략

서버는 vLLM, 개발 PC는 llama.cpp로 정한다. 나열된 기법의 절반은 vLLM에 기본으로 들어 있어 설정만 하면 된다. 직접 설계할 것은 양자화 선택, 접두부 캐시가 적중하는 프롬프트 구조, 요청 종류별 자원 분리 세 가지다.

### 서빙 엔진 비교

| 엔진 | 라이선스 | 강점 | 약점 | 역할 |
| --- | --- | --- | --- | --- |
| vLLM (v0.32.0, 2026-10-18) | Apache 2.0 | 모델·하드웨어 지원 범위가 가장 넓음. 연속 배치, 자동 접두부 캐싱, 구조화 출력 내장 | GPU 전제. 기동과 모델 교체가 느림 | 서버 기본 |
| SGLang (v0.5.23, 2026-11-02) | Apache 2.0 | 접두부를 공유하는 요청(에이전트 루프, 멀티턴)에 강함 | vLLM보다 운영 자료가 적음 | 2단계 비교 후보 |
| llama.cpp | MIT(착수 시 재확인) | CPU와 소형 GPU, GGUF 양자화, 단일 실행 파일 | 동시 처리량이 낮음 | 개발 PC, 소규모 대체 경로 |
| Ollama | MIT(착수 시 재확인) | 설치와 모델 관리가 쉬움 | 동시성과 세부 제어가 제한적 | 개발 편의용. 운영 제외 |

두 엔진의 버전과 비교는 [2026년 11월 기준 비교 자료](https://www.morphllm.com/comparisons/sglang-vs-vllm)를 따랐다. 같은 자료는 접두부 공유가 적은 단발 요청에서는 두 엔진이 비슷하고, 결과가 모델·GPU·배치 크기에 따라 달라진다고 적고 있다. 네 엔진 모두 OpenAI 호환 API를 제공하므로 엔진을 바꿔도 게이트웨이 위쪽은 바뀌지 않는다. SGLang은 2단계에서 실제 부하로 측정해 차이가 클 때만 교체한다.

### 기법별 적용 판단

| 기법 | 해결하는 문제 | 적용 방법 | 판단 |
| --- | --- | --- | --- |
| Quantization | VRAM 부족 | 개발은 GGUF 4비트, 서버는 AWQ·FP8 등 | 적용. 양자화 전후를 평가셋으로 비교 |
| Continuous Batching | 동시 요청 처리량 | vLLM 기본 동작 | 적용 |
| PagedAttention, Flash Attention | KV 캐시 메모리 낭비, 어텐션 연산 속도 | 엔진 내장 | 별도 작업 없음 |
| Prefix Caching | 반복되는 앞부분 재계산, 첫 토큰 지연 | 엔진 기능 + 고정 접두부 프롬프트 구조(9장) | 적용. 에이전트 루프에서 효과가 큼 |
| KV Cache 관리 | 메모리 초과, 과도한 동시 시퀀스 | GPU 메모리 비율, 최대 컨텍스트, 동시 시퀀스 수 설정 | 2단계에서 튜닝 |
| 스트리밍 | 체감 응답 속도 | SSE | 적용 |
| 요청별 토큰 예산, Context Compression | 불필요하게 긴 입력과 출력 | 모드별 출력 상한, 슬롯 예산 | 적용 |
| Speculative Decoding | 단일 요청의 생성 속도 | 초안 모델 또는 n-gram | 2단계 실험. 동시 요청이 많을 때의 이득을 측정한 뒤 결정 |
| Tensor Parallelism | 모델이 GPU 1장에 들어가지 않음 | GPU 여러 장에 가중치 분할 | 필요할 때만. GPU 1장에 들어가는 모델을 우선 |
| 모델 로딩·교체 | 교체 시 수십 초\~수 분 중단 | 상주 모델을 고정하고 요청 중 교체를 하지 않음 | 모델 수를 최소로 유지 |

### 빠른 요청과 긴 작업의 분리

GPU가 2장 이상이면 풀을 둘로 나눈다. 빠른 풀은 작은 모델로 Quick과 분류를 처리하고, 깊은 풀은 큰 모델로 Thinking과 Agent를 처리한다. GPU가 1장이면 모델을 하나만 올리고 우선순위로 나눈다. vLLM은 [우선순위 기반 스케줄링 정책](https://docs.vllm.ai/en/v0.10.0/usage/v1_guide.html)을 지원한다.

- 대화형 요청이 Agent 작업보다 항상 우선한다.
- Agent 작업은 큐에 넣고 동시 실행 수에 상한을 둔다. 상한은 2단계 부하 테스트로 정한다.
- 임베딩과 리랭커는 생성 모델과 다른 프로세스에 둔다. 작은 모델이라 CPU 또는 남는 VRAM으로 충분한지 먼저 측정한다.

## 12. 폐쇄망 및 라이선스 독립성 확보 방안

폐쇄망 독립성은 마지막에 검증하는 항목이 아니라 0단계부터 지키는 개발 규칙이다. 개발 중에 인터넷에 기대는 코드가 쌓이면 마지막 단계에서 한꺼번에 터진다.

### 폐쇄망 독립성

- **네트워크 없는 테스트를 처음부터 돌린다.** 통합 테스트 한 벌을 네트워크를 끈 컨테이너에서 실행한다. 첫 실행 때 모델이나 사전을 내려받는 라이브러리가 여기서 걸러진다.
- **숨은 외부 호출을 끈다.** Hugging Face 오프라인 모드를 켜고, 서빙 엔진과 라이브러리의 사용 통계 전송을 끈다. UI는 글꼴과 스크립트를 모두 빌드 산출물에 포함한다.
- **반입 번들을 하나의 단위로 만든다.** 번들 한 개에 아래가 모두 들어간다.

| 번들 구성 | 형태 | 무결성 확인 |
| --- | --- | --- |
| 컨테이너 이미지 | 이미지 tar 파일 또는 내부 레지스트리 | 이미지 다이제스트 |
| 파이썬 패키지 | 휠 파일 모음. 설치는 외부 색인 없이 로컬 경로에서만 | 해시가 고정된 잠금 파일 |
| 모델 가중치 | safetensors 또는 GGUF | SHA-256 목록. pickle 형식 금지 |
| 보조 모델 | 임베딩, 리랭커, OCR, 레이아웃, 토크나이저, 형태소 사전 | SHA-256 목록 |
| 프런트엔드 | 빌드된 정적 파일 | 빌드 해시 |
| 명세 | SBOM, 라이선스 목록, 취약점 스캔 결과 | 번들 서명 |

업데이트도 번들 단위로 한다. 외부망에서 취약점과 라이선스를 스캔하고, 반입한 뒤 회귀 평가를 통과하면 교체한다. 이전 번들은 롤백용으로 보관한다.

## 13. 보안 및 운영 통제 방안

보안의 중심 원칙은 권한을 모델이 아니라 정책이 정한다는 것이다. 모델이 속거나 틀려도 할 수 있는 일의 범위는 프로필, 데이터 등급, 샌드박스가 정한 만큼으로 한정된다.

| 통제 | 설계 |
| --- | --- |
| 사용자 인증 | OIDC로 사내 인증 체계와 연동. 개발 단계는 로컬 계정, 리허설은 Keycloak |
| 권한 | 역할 기반 권한 + 문서 등급. 대화, 파일, 작업, 기억을 소유자 기준으로 분리. PostgreSQL 행 수준 보안 |
| 문서 보안등급 | 색인할 때 등급 태그 필수. 태그가 없으면 최고 등급으로 취급 |
| 에이전트 최소 권한 | 프로필별 도구 허용 목록. 작업 폴더 밖 파일 접근 불가 |
| Python·Shell 실행 격리 | 작업마다 일회용 컨테이너. 비루트 사용자, 읽기 전용 루트, 네트워크 없음, CPU·메모리·시간·프로세스 수 제한. gVisor 같은 추가 격리 계층 권장 |
| 도구 실행 승인 | 3등급. 읽기는 자동. 작업 폴더 안 쓰기와 코드 실행은 자동 + 기록. 외부에 영향을 주는 행위는 사용자 승인 |
| SQL | 읽기 전용 계정, 행 수 상한, 실행 시간 제한. 쓰기는 초기 범위에서 제외 |
| 외부 통신 통제 | 호스트 방화벽에서 외부행 차단. 컨테이너는 내부 전용 네트워크 |
| 민감정보 마스킹 | 로그와 추적 기록을 저장하기 전에 주민등록번호, 계좌, 카드, 전화번호 패턴을 가림 |
| 감사 로그 | 누가, 언제, 어떤 모델로, 어떤 문서와 도구를 썼는지. 추가 전용, 해시 연쇄, 업무 데이터와 다른 권한 |
| 자원 사용 제한 | 사용자별 동시 요청 수, 일일 토큰, Agent 동시 실행 수 |
| 악성 파일 | 확장자와 실제 형식 대조, 크기·압축비 제한, 매크로 미실행, 격리된 파싱 |
| 공급망 | 해시 고정 설치, 내부 미러, SBOM, 취약점·라이선스 스캔, 가중치 해시 검증 |

### 프롬프트 인젝션

프롬프트 인젝션은 완전히 막을 수 없다고 가정한다. 방어는 탐지가 아니라 피해 범위를 줄이는 구조에 둔다.

1. 문서, 검색 결과, 도구 결과는 데이터 구획에 넣고 지시로 따르지 않도록 프롬프트에 명시한다. 이것만으로는 부족하다.
2. 도구 권한은 콘텐츠가 아니라 프로필이 정한다. 문서 안의 문장이 새 도구를 열 수 없다.
3. 외부에 영향을 주는 행위는 사람이 승인한다.
4. 샌드박스에 네트워크가 없으므로, 속은 모델이 데이터를 내보낼 경로가 없다.
5. 검색에 권한 필터가 걸려 있으므로, 속은 모델도 사용자 등급을 넘는 문서를 읽을 수 없다.

### 운영 관점의 책임

결과물에는 AI가 생성했다는 사실과 검증한 범위를 표시한다. 첨부 가이드의 '통제된 자율' 원칙에 따라 최종 판단과 책임은 사용자에게 둔다. 내부 이식 전에는 정보보호 부서의 레드팀 점검(인젝션, 샌드박스 탈출, 권한 우회)을 받는다.

## 14. 기술 스택 선정 근거와 대안 비교

선정 기준은 구성요소 수를 늘리지 않는 것이다. 기성 플랫폼을 조합하는 대신, 검증된 부품(DB, 서빙 엔진, 파서, 상태 그래프) 위에 얇은 자체 코드를 올린다. 라이선스 열의 '재확인'은 이번 조사에서 원문을 열어보지 못한 항목이다.

| 영역 | 선정 | 라이선스 | 선정 이유 | 대안과 보류 사유 |
| --- | --- | --- | --- | --- |
| 백엔드 | Python + FastAPI | MIT(재확인) | AI 라이브러리 생태계, 비동기 스트리밍 | 해당 없음 |
| 저장소 | PostgreSQL + pgvector | PostgreSQL License | 업무 데이터, 벡터, 체크포인트, 작업 큐, 감사 로그를 한 곳에 | Qdrant·Milvus: 별도 서비스가 늘어남. 규모가 커지면 검토 |

| 문서 파싱 | Docling + pypdfium2 | MIT, Apache·BSD(재확인) | 8장 참조 | MinerU, PyMuPDF: 라이선스 |
| 임베딩·키워드 | KURE-v1 또는 BGE-M3, Kiwi | MIT, LGPL v3 | 9장 참조 | 출처 심사 결과에 따라 교체 |
| 샌드박스 | 컨테이너(Docker 또는 Podman) + gVisor | Apache 2.0(재확인) | 사내 표준 컨테이너 런타임을 그대로 사용 | 마이크로VM: 운영 복잡 |
| UI | React 기반 자체 구현 | MIT(재확인) | 모드 선택과 작업 진행 표시가 핵심 화면 | Open WebUI: 브랜딩 조항. 다른 오픈소스 채팅 UI: 의존 서비스가 많음 |
| 평가 | pytest 기반 자체 러너 + 평가셋 파일 | MIT(재확인) | 검사 로직이 코드라 회귀 테스트와 동일하게 운영 | 평가 프레임워크: 지표 구현만 참고 |
| 관측 | 추적 기록을 PostgreSQL에 저장 + 엔진의 메트릭 | 해당 없음 | 별도 관측 플랫폼 없이 시작 | LLM 관측 플랫폼: 의존 서비스가 많아 후순위 |
| 부하 테스트 | Locust | MIT(재확인) | 혼합 시나리오를 파이썬으로 작성 | 엔진 전용 벤치마크 도구: 엔진 단독 측정에 병행 |
| 배포 | Docker Compose | Apache 2.0(재확인) | 서버 1\~2대 규모에 충분 | Kubernetes: 사내 표준이면 이식 단계에서 전환 |

의도적으로 넣지 않은 것은 메시지 브로커, 별도 벡터 DB, 별도 검색 엔진, 에이전트 프레임워크 중복, 관측 플랫폼이다. 각각 평가에서 한계가 측정될 때 추가한다. 어느 것도 모듈 인터페이스 뒤에 있어 나중에 끼울 수 있다.

## 15. 개발 단계 및 우선순위 (PC·Colab → RunPod → 폐쇄망 유사 서버)

개발은 다섯 단계로 가고, 계획하신 순서(PC·Colab → RunPod → 정리 → 사내 유사 서버)를 그대로 따른다. 다만 Colab과 RunPod의 역할은 플랫폼 제약 때문에 예상보다 좁게 잡아야 한다.

&#91;embedded content: 개발 로드맵 · 5단계, 관문 4개\]

각 상자는 단계와 그 단계의 실행 환경이고, 마름모는 다음 단계로 넘어가는 조건이다. 상세 기준은 16장에 있다.

### 개발 환경의 제약

| 환경 | 확인된 제약 | 이 설계에서의 역할 |
| --- | --- | --- |
| [Colab Pro](https://research.google.com/colaboratory/faq.html) | 노트북 실행은 일반적으로 최대 12시간, 유휴 시 종료. 대화형 연산과 무관한 웹 서비스 제공과 원격 프록시 연결은 모든 런타임에서 금지 | 플랫폼의 상시 모델 서버로 쓰지 않는다. 노트북 안에서 모델을 올려 평가셋을 배치로 돌리고 결과 파일을 내려받는 모델 벤치마크 용도 |
| [RunPod Pod](https://docs.runpod.io/pods/overview) | Pod 자체가 컨테이너라 Docker Compose를 쓸 수 없고 자체 Docker를 띄울 수 없음. TCP·HTTP만 지원 | 모델 서버(vLLM)만 올린다. API 서버, DB, 샌드박스는 Docker가 되는 호스트(개발 PC 또는 일반 VM)에 둔다 |
| 사내 유사 서버 | OS와 네트워크를 직접 통제할 수 있어야 함 | 오프라인 설치, 샌드박스 격리, 외부 통신 차단 검증. RunPod Pod로는 이 검증을 할 수 없다 |

3장의 구조에서 모델 서버만 따로 떼어 둔 것이 이 제약과 맞는다. 2단계에서 바뀌는 것은 레지스트리의 모델 서버 주소뿐이다.

### 단계별 작업

| 단계 | 모델 | 하는 일 |
| --- | --- | --- |
| 0. 기반 | 개발 PC에서 도는 소형 모델(4비트 GGUF) | 저장소 구조와 모듈 인터페이스, 게이트웨이, Quick 채팅, 컨텍스트 예산 조립기, 평가 러너와 평가셋 초판, 네트워크 없는 테스트 |
| 1. 기능 개발 | 소형 모델. Colab에서 중형 후보 벤치마크 | 전 모듈 구현. 모든 경로가 동작하는지 확인 |
| 2. 서버 검증 | 목표 규모 모델. 사내에 들어갈 GPU와 같은 급으로 대여 | 모델 후보 평가와 확정, 라우팅 기준값, 성능 튜닝, 부하 테스트, 기법별 켜고 끈 비교 |
| 3. 정리 | 확정 모델 | 효과가 측정되지 않은 기능과 코드 삭제, 의존성 축소, 오프라인 번들, 설치·운영 문서 |
| 4. 폐쇄망 리허설 | 확정 모델 | 16장의 7개 항목 검증, 이식 판정 |

2단계의 GPU는 성능이 좋은 것이 아니라 사내에 실제로 놓일 것과 같은 급으로 빌린다. 더 큰 GPU에서 맞춘 모델과 설정은 이식할 때 다시 해야 한다. 사내 GPU 규모가 정해지지 않았다면 두 가지 급(예: 24\~48GB 1장, 80GB 1장)으로 각각 측정해 도입 규모 결정의 근거로 쓴다.

### 1단계 안의 구현 순서

앞 항목이 뒤 항목의 전제다. 특히 검증기 없이 Workflow Engine을 먼저 만들면 루프가 돌기만 하고 멈출 근거가 없다.

1. 파일 파이프라인과 공통 문서 표현
2. RAG와 권한 필터
3. 도구와 샌드박스
4. Agent Runtime과 구조화 출력. Thinking 모드가 여기서 완성된다
5. 검증기
6. Workflow Engine과 템플릿 3종, 진행 표시 UI
7. Auto 라우터
8. 감사 로그, 사용량 제한 등 운영 통제 보강

## 16. 단계별 산출물과 검증 기준

모든 검증 기준은 자체 평가셋과 자동 테스트로 판정한다. 평가셋은 0단계에서 업무 유형당 10\~20문항으로 시작해 실패 사례를 계속 편입한다. 문항마다 입력, 첨부, 그리고 코드로 작성한 채점기를 갖는다.

| 단계 | 산출물 | 관문 통과 기준 |
| --- | --- | --- |
| 0. 기반 | 저장소 구조, 모듈 인터페이스, 게이트웨이, Quick 채팅, 컨텍스트 예산 조립기, 평가 러너, 평가셋 초판 | 채팅이 끝에서 끝까지 동작. 평가 러너가 점수표를 출력. 네트워크 없는 테스트 통과 |
| 1. 기능 개발 | 파일 파이프라인, RAG, Agent Runtime, 샌드박스, 검증기, Workflow Engine, 진행 표시 UI, 권한·등급, 모델 후보 벤치마크 노트북 | 소형 모델로 평가셋의 모든 경로가 오류 없이 실행됨. 권한 테스트 전 항목 통과. 이 단계에서는 정답률이 아니라 경로의 동작을 본다 |
| 2. 서버 검증 | 모델별 평가 결과표, 라우팅 설정, 성능 튜닝 값, 부하 테스트 보고서, 기법별 효과 측정표 | 확정 모델이 업무 유형별 합격선을 넘음. 목표 동시 사용자 수에서 지연과 오류율이 기준 이내 |
| 3. 정리 | 축소된 코드와 의존성, 오프라인 번들, 설치·운영 문서, SBOM | 정리 후 평가 점수가 2단계 대비 하락하지 않음. 번들만으로 깨끗한 환경에 설치 성공 |
| 4. 폐쇄망 리허설 | 7개 항목 검증 보고서, 이식 판정 자료 | 아래 표의 전 항목 통과 |

합격선과 목표 동시 사용자 수는 이 설계서가 정하지 않는다. 합격선은 1단계 말에 기준선을 잰 뒤 정하고, 동시 사용자 수는 내부 도입 범위가 정해져야 나온다.

## 17. 예상되는 기술적 한계와 해결 방안

가장 큰 한계는 제한된 GPU에서 돌릴 수 있는 모델의 Agent 모드 성공률이다. 이 값은 2단계에서 실측하기 전까지 알 수 없다. 그래서 Agent 모드의 업무 적용 범위는 2단계 결과를 보고 정한다.

| 한계 | 영향 | 대응 |
| --- | --- | --- |
| 소형 모델의 다단계 작업 성공률이 낮음 | 1단계에서 Agent 모드가 자주 실패 | 1단계는 경로 동작만 확인. 품질 판단은 2단계 목표 모델로 |
| 도구 호출 형식이 불안정 | 잘못된 인자, 없는 도구 호출 | 스키마 제약 출력, 단계별 도구 수 축소, 인자 구조 단순화 |
| 긴 작업에서 오류가 누적 | 뒤로 갈수록 엉뚱한 방향 | 단계별 컨텍스트 격리, 단계마다 검증, 예산 상한 |
| 같은 모델의 자기 검증은 맹점을 공유 | 틀린 결과를 통과시킴 | 실행·규칙 검증 우선. 검증할 수 없는 부분은 결과물에 '미검증'으로 표시 |
| 모델이 쓴 테스트가 허술함 | 테스트는 통과하나 요구사항 미충족 | 완료 조건을 사용자가 승인. Reviewer가 조건별 테스트 존재를 확인 |
| HWP 구버전, 복잡한 서식, 저품질 스캔 | 파싱 실패 또는 표 깨짐 | 실패를 숨기지 않고 안내. PDF 재업로드 경로. 파싱 품질을 평가셋에 포함 |
| 비전 모델의 작은 글씨·복잡한 차트 인식 | 수치를 잘못 읽음 | OCR 텍스트 병행. 수치가 중요한 업무는 원본 데이터 파일 요구 |
| GPU 1\~2장의 동시 처리 한계 | 사용자가 늘면 지연 급증 | 우선순위, 대기열, Agent 동시 실행 상한. 포화 지점을 실측해 안내 |
| 모델 교체 비용 | 프롬프트 반응, 도구 호출, 한국어 품질이 함께 바뀜 | 모델별 프롬프트 패치, 회귀 평가, 교체에 걸린 기간을 지표로 관리 |
| 게이트웨이가 단일 장애점 | 게이트웨이 장애 시 전면 중단 | 무상태로 구현해 다중화 가능하게 유지 |
| 한국어 검색 품질 | 정답 문서를 못 찾음 | 형태소 기반 키워드 검색 병행, 리랭커, 검색 평가셋 |
| 평가셋 구축 비용 | 현업 전문가의 시간이 필요 | 작게 시작. 운영 중 실패 사례를 편입 |
| 개발 환경과 폐쇄망의 차이 | 이식 단계에서 숨은 외부 의존 발견 | 0단계부터 네트워크 없는 테스트 |

하네스 기법이 늘어날수록 호출 수와 지연도 늘어난다. 그래서 기법마다 켜고 끄는 설정을 두고, 2단계에서 켬 경우와 끈 경우의 평가 점수를 비교한다. 효과가 측정되지 않는 기법은 3단계에서 코드째 삭제한다.

## 18. 초기 개발 범위와 향후 확장 범위

초기 범위는 세 가지 업무(문서 분석, 데이터 분석, 프로그램 개발)를 세 모드로 끝까지 수행하는 데 필요한 최소 구성이다. 나머지는 인터페이스만 열어 두고 미룬다.

| 영역 | 초기 범위(1\~2단계) | 여유가 있으면(3단계 이전) | 이식 후 확장 |
| --- | --- | --- | --- |
| UI | 채팅, 파일 첨부·관리, 모드·모델 선택, 진행 표시, 이력, 다운로드 | 첨부 미리보기 고도화 | 관리자 콘솔, 평가 대시보드 |
| 모델 | 내부 모델 1\~2개, 장애 전환, 등급 태그 전달 | 빠른 풀·깊은 풀 분리 | 상용 모델 어댑터, 학습형 라우터 |
| 파일 | PDF, Word, Excel, PowerPoint, HWPX, 이미지, CSV, 코드 | HWP 바이너리 변환 | 서식별 전용 추출기 |
| 지식 | 첨부 기반 검색, 사내 문서 검색, 권한 필터, 출처 표시 | 리랭커 | 사내 시스템 연동 수집기 |
| 기억 | 대화, 작업 기억, 이력 조회, 수동 장기 기억 | 유사 작업 참조 | 장기 기억 자동 추출 |
| 도구 | Python 실행, 파일 읽기·생성, 데이터 분석, 문서 변환, 검색 | 읽기 전용 SQL | REST, MCP 서버 연결 |
| 워크플로 | 템플릿 3종: 문서 분석, 데이터 분석, 프로그램 개발 | 보고서 작성 템플릿 | 업무별 템플릿, 자율 단계 확대 |
| 검증 | 테스트, 스키마, 규칙, 인용 확인, Reviewer | 보안 정적 분석 연동 | UI 시각 검수 |
| 성능 | 양자화, 접두부 캐싱, 스트리밍, 토큰 예산 | Speculative Decoding 실험, SGLang 비교 | 다중 GPU, 다중 노드 |
| 운영 | 인증, 권한, 등급, 감사 로그, 샌드박스, 평가 러너 | 사용량 한도 | 사내 인증 연동, Kubernetes |

MCP는 초기에 구현하지 않지만 자리를 마련해 둔다. 내장 도구의 정의 형식(이름, 설명, JSON 스키마 입력)을 MCP와 같게 맞추면 나중에 MCP 서버를 도구 목록에 그대로 연결할 수 있다. 사내 시스템 연동은 시스템마다 MCP 서버를 하나씩 붙이는 방식으로 확장한다.

상용 모델 확장은 기술 작업보다 선행 조건이 더 크다. 데이터 등급 기준의 확정, 대체 정보보호통제 충족 여부, 법무 검토가 먼저 끝나야 한다(첨부 가이드 12장 확인 목록). 플랫폼 쪽 작업은 6장에 적은 세 가지로 끝난다.
